## Задание 1. Docker. Начало работы

### Цель

Проверить работу Docker и освоить запуск контейнера, переменные окружения, тома, проброс портов и сеть между контейнерами.

### Ход работы

Docker Desktop установлен, демон отвечает на `docker version`.

Проверочный контейнер:

```bash
docker run --rm hello-world
```

Образ скачан из Docker Hub. В терминале выведено `Hello from Docker!`. Клиент связался с демоном, демон создал контейнер, контейнер напечатал сообщение и завершился.

Дальше по методичке выполняются такие действия.

1. Контейнер Ubuntu без долгого процесса сразу останавливается, к нему нельзя подключиться через `docker attach`. Его удаляют и создают заново с оболочкой:

```bash
docker run -it --name MyUbuntu2204 ubuntu:22.04 /bin/bash
```

2. Переменная окружения задаётся флагом `-e`. Внутри контейнера `echo $MyVar` печатает `TTIT`:

```bash
docker run -it -e "MyVar=TTIT" --name MyUbuntu2304 ubuntu:23.04 /bin/bash
```

3. Каталог хоста монтируется в контейнер флагом `-v`. Файлы, созданные на хосте, видны по внутреннему пути.
4. Nginx публикует порт 80 контейнера как порт 8080 хоста. Страница открывается по адресу `http://127.0.0.1:8080`:

```bash
docker run --name MyWebServer -p 8080:80 -d nginx
```

5. MySQL хранит данные в томе `mysql_volume`. Пароль суперпользователя передаётся переменной `MYSQL_ROOT_PASSWORD`. phpMyAdmin сначала связывается с базой через `--link`, затем оба контейнера переносятся в сеть `docker_network`. В общей сети база доступна по имени контейнера `MySQL` (`PMA_HOST=MySQL`).

Полный список команд записан в `01-docker/commands.md`. Порт phpMyAdmin в этих командах — 8081, потому что 8080 уже занимает Nginx. В методичке оба примера используют 8080 по очереди: контейнер Nginx перед этим удаляют.

### Определения

- **Docker** — платформа, которая упаковывает приложение вместе со средой выполнения и запускает его изолированно от остальной системы.
- **Образ** — неизменяемый шаблон контейнера: код, зависимости, настройки. Тег (`nginx:latest`, `ubuntu:22.04`) выбирает конкретный снимок. Из одного образа создаётся любое число контейнеров.
- **Контейнер** — запущенный из образа процесс со своей файловой системой и сетью. Контейнер жив, пока жив его главный процесс.
- **Docker Hub** — публичный реестр образов. Если образа нет локально, `docker run` скачивает его оттуда.
- **Dockerfile** — рецепт своего образа: `FROM`, `RUN`, `COPY`, `ENV`, `EXPOSE`, `CMD`.
- **Том** — хранилище, которое переживает удаление контейнера. Без тома или примонтированного каталога данные контейнера пропадают вместе с ним.
- **Проброс портов** — публикация порта контейнера на хост. Запись `8080:80` означает порт 80 внутри и порт 8080 снаружи.
- **Сеть Docker** — виртуальная сеть, в которой контейнеры обращаются друг к другу по имени. Для нескольких сервисов она удобнее цепочки `--link`.
- **Docker Compose** — описание группы контейнеров в одном YAML-файле и запуск этой группы одной командой.
- **Демон и клиент** — демон выполняет операции с контейнерами, команда `docker` передаёт ему запросы.

### Вывод

Контейнер изолирует один процесс. Порты наружу сами не открываются, данные без тома не сохраняются, а общая сеть заменяет ручное связывание контейнеров.

## Задание 2. Docker Compose

### Цель

Поднять веб-приложение из нескольких контейнеров одним файлом: Nginx, PHP-FPM, MariaDB и phpMyAdmin.

### Ход работы

Проект находится в `02-docker-compose`. Файл `docker-compose.yaml` использует синтаксис версии 3.5 и секции `networks`, `volumes`, `services`.

- `docker-nginx` публикует порт 8094 и монтирует каталог проекта в `/var/www/html`.
- `docker-mariadb` хранит данные в томе `ttit-vl`. Учётные данные: root / `root`, база `app`, пользователь `user` / `password`.
- `docker-phpmyadmin` доступен на порту 8095 и подключается к базе по имени сервиса `docker-mariadb`.
- `docker-php-fpm` собирается из `php-fpm/Dockerfile` (`php:8.3-fpm` и расширения `pdo_mysql`, `mysqli`).
- `nginx/site.conf` отдаёт `index.html` и передаёт файлы `*.php` процессу PHP-FPM. Один и тот же каталог смонтирован в оба контейнера как `/var/www/html`, поэтому PHP находит файл скрипта.

Запуск:

```bash
cd 02-docker-compose
docker compose up --build -d
```

### Результат

| Адрес | Ответ |
| --- | --- |
| http://127.0.0.1:8094/ | своя HTML-страница Nginx |
| http://127.0.0.1:8094/index.php | `PHP version: 8.3.36` |
| http://127.0.0.1:8095/ | страница входа phpMyAdmin, код 200 |

Остановка: `docker compose stop`. Удаление контейнеров с сохранением тома: `docker compose down`.

### Вывод

Compose заменяет набор отдельных команд `docker run`. Сервисы одной сети видят друг друга по имени, а файлы сайта остаются на хосте и меняются без пересборки образа Nginx.

## Задание 5. Автоматическая сборка CI/CD

### Цель

Собрать приложение Node.js в образ и описать GitHub Actions, который по push в ветку `main` публикует образ на Docker Hub.

### Ход работы

`05-cicd/app.js` поднимает Express на порту 4000. `GET /` отвечает `Hello World!!`.

Локальный образ:

```bash
cd 05-cicd
docker build . --tag node_app
docker run --rm -p 4000:4000 node_app
```

Проверка: `http://127.0.0.1:4000/` вернул `Hello World!!`, код 200.

В методичке базовый образ `node:19` и строка `CMD = ["npm","run","start"]`. Метка `node:19` снята с поддержки, а знак `=` в инструкции `CMD` делает Dockerfile невалидным. В работе использован `node:20-alpine` и команда `CMD ["npm", "run", "start"]`.

Workflow называется `node_app` и запускается на push в `main`. Шаги: получить код, войти в Docker Hub, подготовить Buildx, собрать образ и отправить тег `<логин>/clockbox:latest`. Версии actions обновлены до `checkout@v4`, `login-action@v3`, `setup-buildx-action@v3`, `build-push-action@v6`: старые версии из статьи на текущих раннерах GitHub уже не запускаются. Смысл шагов тот же.

Файл workflow приложения: `05-cicd/.github/workflows/main.yml`. GitHub читает workflow только из корня репозитория, поэтому тот же конвейер продублирован в `.github/workflows/node-app.yml` и собирает каталог `05-cicd`.

Секреты репозитория, которые нужно создать в GitHub (Settings → Secrets and variables → Actions):

- `DOCKERHUB_USERNAME` — логин Docker Hub
- `DOCKERHUB_TOKEN` — access token из Account settings → Security

Токен показывается один раз и в репозиторий не записывается.

### Вывод

Push в `main` запускает сборку и публикацию образа. Учётные данные остаются в секретах GitHub, поэтому их нет в коде.

## Задание 6. CRUD API на Rust, Postgres и Docker

### Цель

Сделать HTTP API пользователей на Rust, хранить записи в Postgres и запускать оба сервиса через Docker Compose.

### Ход работы

Проект `06-rust-crud` повторяет схему Francesco Ciulla (Rust CRUD Rest API).

Модель `User`: необязательный `id`, обязательные `name` и `email`. Идентификатор выдаёт столбец `SERIAL`. Поле `id` помечено `#[serde(default)]`, поэтому пользователя можно создать телом без идентификатора.

Сервер слушает `0.0.0.0:8080` через `TcpListener`, без веб-фреймворка. Маршруты:

- `POST /users` — создать
- `GET /users` — список
- `GET /users/{id}` — одна запись
- `PUT /users/{id}` — изменить
- `DELETE /users/{id}` — удалить

Адрес базы вшивается при компиляции: `env!("DATABASE_URL")`. При старте создаётся таблица `users`, если её ещё нет. Подключение повторяется до 30 раз с паузой 2 секунды: Postgres в соседнем контейнере принимает соединения не сразу.

Dockerfile многоступенчатый. Стадия сборки ставит `libpq-dev` и выполняет `cargo build --release`. Стадия запуска копирует только бинарник и библиотеку `libpq5`. В методичке указаны образы `rust:1.69-buster` и `debian:buster-slim`. Они сняты с публикации, а текущие крейты требуют Rust с edition 2024, поэтому сборка идёт на `rust:1-bookworm` и `debian:bookworm-slim`.

```bash
cd 06-rust-crud
docker compose up --build -d
```

Строка подключения: `postgres://postgres:postgres@db:5432/postgres`. Хост `db` — имя сервиса Postgres. Данные базы лежат в томе `pgdata`.

### Результат

| Запрос | Ответ |
| --- | --- |
| `GET /users` на пустой базе | `200 []` |
| `POST /users` с именем Ivan | `200 User created` |
| `GET /users` | пользователь с `id` 1 |
| `GET /users/1` | та же запись |
| `PUT /users/1` | `200 User updated` |
| `DELETE /users/1` | `200 User deleted` |

### Вывод

API обошёлся стандартной библиотекой и драйвером Postgres. Compose связал приложение с базой по имени сервиса, а в итоговом образе остался только бинарник, без компилятора Rust.

## Задание 7. GitHub Pages

### Цель

Собрать клиент на React и TypeScript, в разработке читать данные из json-server, в продакшене — из файлов ветки `gh-pages`, и опубликовать сборку.

### Ход работы

Исходники Create React App лежат в `07-github-pages`.

Локальные данные:

- `src/server/db/data.json` — `{ "greeting": "Hello world" }`
- `src/server/db/index.js` — отдаёт эти данные json-server
- `src/server/routes.json` — префикс `/api/*` переписывается в `/$1`
- `npm run serve` запускает json-server на порту 3001

`src/api/index.ts` в режиме development запрашивает `http://localhost:3001/api/data`. В production адрес строится так:

`https://raw.githubusercontent.com/<пользователь>/up-docker-labs/gh-pages/static/db/data.json`

Имя пользователя задаётся в `src/config.ts` (`GITHUB_USER`). Сейчас там стоит `YOUR_GITHUB_USERNAME`: его нужно заменить перед публикацией.

`App.tsx` при запуске вызывает `api.get.data()` и показывает `greeting`.

После `npm run build` скрипт `save-json-api.js` копирует данные в `build/static/db`. Команда `shx cp build/index.html build/404.html` кладёт в сборку копию страницы для неизвестных адресов: GitHub Pages иначе не отдаст клиентское приложение. `npm run deploy` публикует каталог `build` в ветку `gh-pages` пакетом `gh-pages`. Поле `homepage` равно `.`, поэтому пути к скриптам и стилям относительные.

В настройках репозитория: Settings → Pages → Deploy from branch → ветка `gh-pages`. Сайт открывается по адресу `https://<пользователь>.github.io/up-docker-labs/`.

Запуск локально, в двух терминалах:

```bash
cd 07-github-pages
npm install
npm run serve
npm start
```

Клиент будет на http://localhost:3000 и покажет `Hello world`.

### Вывод

Один клиент в разработке читает json-server, а в сборке — файл из ветки `gh-pages`. Выбор адреса находится в функции `getJson` и зависит от `NODE_ENV`.

## Задание 8. Окружения dev и prod

### Цель

Разделить разработку и продакшен: два файла Compose, общий `.env`, контейнеры Node.js, Nginx, Postgres и pgAdmin.

### Ход работы

Каталог `08-dev-prod`.

`.env` задаёт `NODE_ENV=dev`, базу `api`, пользователя `postgres`, пароль `secret007`, хост `db` и файл `COMPOSE_FILE=docker-compose.dev.yml`. Compose не подставляет переменные внутри самого `.env`, поэтому имя файла записано целиком. Для продакшена меняются две строки: `NODE_ENV=production` и `COMPOSE_FILE=docker-compose.production.yml`.

Отличия окружений:

- dev собирает цель `dev`, монтирует исходники и оставляет контейнер запущенным, чтобы войти внутрь и стартовать nodemon;
- production собирает цель `production`, выполняет `npm i` при сборке, запускает `npm run start` и хранит `node_modules` в отдельном томе, чтобы каталог хоста их не затёр.

`app.js` на `GET /` отвечает `{ "message": "Hello World" }`. При старте выполняется `SELECT NOW()`. Пул соединений после проверки не закрывается, иначе сервер потерял бы доступ к базе.

Nginx отдаёт файлы из `static` (проверка: http://localhost/file.txt) и проксирует остальные запросы на `app:3000`. Путь `/pgadmin` ведёт в pgAdmin. Вход: `info@proglib.io` / `qwertyuiop`.

Базу `api` образ Postgres сам не создаёт. Её создают в pgAdmin (сервер `db`, пользователь `postgres`, служебная база `postgres`) или командой:

```bash
docker compose exec db psql -U postgres -c "CREATE DATABASE api;"
```

Запуск разработки:

```bash
cd 08-dev-prod
docker compose up --build -d
docker compose exec app sh
npm install
npm run dev
```

Оба compose-файла проверены командой `docker compose config`: конфигурация разбирается без ошибок.

В методичке базовый образ `node:16.10.0-alpine`. Эта метка больше не публикуется, в Dockerfile стоит `node:18-alpine`. Часовой пояс — `Europe/Moscow`.

### Вывод

Код, Nginx и база общие. Окружение выбирается целью сборки и значением `COMPOSE_FILE`: в разработке исходники монтируются и перезапускаются nodemon, в продакшене зависимости ставятся внутрь образа.
